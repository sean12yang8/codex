# 微信小游戏（中国风大富翁）技术方案（MVP）

## 1. 产品目标

打造一款 2~4 人实时对局的微信小游戏，保留经典大富翁核心玩法：

- 匹配开局（自动匹配玩家）。
- 房间开局（自建房+邀请好友）。
- 回合制掷骰子、移动、购买资产、支付过路费。
- 中国风主题资产（城市、运河电站、机场等）。

MVP 阶段先保证“可稳定开局+可完整打完一局”，再扩展道具、卡牌、活动和段位。

---

## 2. 核心功能拆解

### 2.1 微信认证登录

1. 客户端调用 `wx.login()` 获取临时 `code`。
2. 客户端将 `code` 传给后端 `POST /auth/wechat/login`。
3. 后端通过微信接口换取 `openid` / `session_key`，并签发业务 `JWT`。
4. 建立玩家资料：昵称、头像、默认金币、历史战绩。

> 说明：仅把 `openid` 当唯一用户标识，敏感信息不落客户端。

### 2.2 自动匹配

- 玩家点击“开始匹配”，进入匹配池。
- 按条件聚合：
  - 模式（经典/快速）
  - 人数（2人/4人）
  - 网络质量与等待时长
- 当池中满足人数时，创建 `matchId + roomId`，广播进入对局。
- 超时策略：超过 N 秒可放宽条件（如优先凑满 4 人，不足则降为 2 人局）。

### 2.3 自建房与邀请

- 玩家点击“创建房间”，生成 `roomCode`（6 位）。
- 可配置：
  - 最大人数（2~4）
  - 初始金币
  - 回合时间
- 分享到微信好友后，其他玩家通过 `roomCode` 加入。
- 房主点击“开始游戏”后锁房，不允许中途加入。

### 2.4 回合制大富翁对局

每局流程：

1. 初始化棋盘与玩家出生点。
2. 按顺序轮到玩家行动。
3. 玩家掷骰子 -> 前进 N 格。
4. 结算落点事件：
   - 无主资产：可购买
   - 他人资产：支付过路费
   - 特殊格（税务、机遇、监狱等）：执行事件
5. 玩家可执行附加操作（升级地产、使用卡片等，MVP 可选）。
6. 回合结束，切换下一位。
7. 触发结束条件：
   - 仅剩 1 名未破产玩家
   - 达到最大回合数后按总资产排名

## 3. 中国风内容设计建议

### 3.1 资产类型

- **城市地块**：如“长安、洛阳、苏州、临安”。
- **运河电站**（类公共事业）：收益受骰子点数影响。
- **机场**（类交通枢纽）：持有数量越多，过路费越高。
- **名胜地标**（高级地块）：高购置价+高回报。

### 3.2 视觉与叙事

- UI 采用水墨、印章、卷轴风格。
- 音效使用古筝/笛子短音作为回合反馈。
- 事件卡改名为“机缘签”“朝廷令”等中国风文案。

## 4. 系统架构（推荐）

## 4.1 架构分层

1. **微信小游戏前端**
   - 渲染棋盘、角色、动画
   - 管理输入与弱网重连
2. **游戏网关服务（HTTP + WebSocket）**
   - 鉴权、路由、连接管理
3. **匹配服务**
   - 匹配池管理、组队开局
4. **房间/对局服务（Game Server）**
   - 权威状态机（骰子、移动、资产结算）
5. **数据服务（MySQL + Redis）**
   - MySQL：用户、资产配置、战绩
   - Redis：在线会话、匹配队列、房间瞬时态

### 4.2 技术选型（可落地）

- 前端：微信小游戏原生 + TypeScript。
- 后端：Node.js（NestJS）或 Go（Gin/Fiber）。
- 实时通信：WebSocket。
- 数据库：MySQL + Redis。
- 部署：Docker + 云托管（腾讯云优先）。

## 5. 数据模型（MVP）

### 5.1 玩家表 `players`

- `id`（PK）
- `openid`（UNIQUE）
- `nickname`
- `avatar_url`
- `coins`
- `rank_score`
- `created_at`

### 5.2 房间表 `rooms`

- `id`（PK）
- `room_code`（UNIQUE）
- `owner_player_id`
- `max_players`（2~4）
- `status`（waiting/playing/finished）
- `created_at`

### 5.3 对局表 `matches`

- `id`（PK）
- `room_id`
- `mode`
- `seed`（随机种子，便于复盘）
- `status`
- `winner_player_id`
- `created_at`, `ended_at`

### 5.4 对局玩家状态 `match_players`

- `id`（PK）
- `match_id`
- `player_id`
- `position`
- `cash`
- `is_bankrupt`
- `turn_order`

### 5.5 资产实例 `match_properties`

- `id`（PK）
- `match_id`
- `tile_id`
- `owner_player_id`
- `level`

## 6. 核心服务接口（示例）

### 6.1 HTTP API

- `POST /auth/wechat/login`
- `POST /matchmaking/join`
- `POST /matchmaking/cancel`
- `POST /rooms/create`
- `POST /rooms/join`
- `POST /rooms/start`
- `GET /matches/{id}/snapshot`

### 6.2 WebSocket 事件

客户端上行：

- `ws:ready`
- `ws:roll_dice`
- `ws:buy_property`
- `ws:end_turn`

服务端下行：

- `ws:match_found`
- `ws:game_started`
- `ws:turn_changed`
- `ws:dice_result`
- `ws:player_moved`
- `ws:tile_settlement`
- `ws:game_over`

## 7. 对局状态机（防作弊重点）

必须由服务端做“权威判定”，客户端只做展示：

- 客户端请求 `roll_dice`。
- 服务端校验“是否当前玩家+是否可掷骰”。
- 服务端生成随机点数（可基于 `seed + turn`），并广播。
- 服务端执行移动与结算，写入事件日志。
- 客户端根据广播动画播放，不得自行改状态。

这样可避免“改包刷点数、篡改金币”等作弊。

---

## 8. 断线重连与容错

- 玩家掉线：
  - `grace period`（如 60 秒）内允许重连恢复。
  - 超时后托管（AI/自动结束回合）。
- 服务端定期快照 `match snapshot` 到 Redis。
- 客户端重连后拉取快照 + 增量事件恢复。

---

## 9. 安全与合规

- 登录态使用短期 JWT + 刷新机制。
- 关键接口限流（防刷匹配、防爆破房间号）。
- 聊天与昵称需接入内容安全审核。
- 保存必要日志，支持争议对局回放。

## 10. 里程碑计划（8 周）

### 第 1-2 周：基础搭建

- 微信登录打通
- 玩家系统 + 大厅 UI
- WebSocket 基础通信

### 第 3-4 周：匹配与房间

- 自动匹配池
- 创建房间/邀请码/入房
- 对局初始化

### 第 5-6 周：核心玩法

- 掷骰、移动、买地、收费
- 破产与胜负判定
- 断线重连

### 第 7 周：打磨与平衡

- 数值调优
- 新手引导
- 动画和音效优化

### 第 8 周：灰度与上线准备

- 压测与异常演练
- 数据埋点
- 提审与发布

---

## 11. MVP 验收标准（建议）

- 4 人自动匹配平均耗时 < 20 秒（高峰期）。
- 自建房邀请成功率 > 99%。
- 单局完整结束率 > 95%。
- 断线 60 秒内重连恢复成功率 > 98%。
- 核心作弊事件（骰子篡改）可被 100% 拦截。

---

## 12. 你可以马上开始的执行清单

1. 确定 MVP 棋盘：先做 24 格（城市/机场/运河/事件格）。
2. 先实现“2 人局完整跑通”，再扩展到 4 人。
3. 优先完成服务端状态机，再补客户端表现层。
4. 本周先交付：登录、匹配、入局、掷骰移动。
